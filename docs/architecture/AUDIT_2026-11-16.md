# Flutter maintainability audit — 16 November 2026

What this repo does: ERP Workspace is a desktop/mobile Flutter front end for ERPNext/Frappe, with a company-enabled knitting pack, document workflows, finance and read-only original history. Expected load is one active account/company per app session, multiple concurrently open routes, and concurrent backend users. This is an architecture audit of the Flutter app, not a full backend security audit.

No application code was changed during this audit. The baseline includes existing uncommitted work. [Inventory](BASELINE_INVENTORY.md): 74 source files, 37,786 lines, 181 public top-level declarations, 84 test files and 93 resolved packages. The AST inventory parsed every source/test/tool file. End-to-end reads concentrated on transport/session/access, document writes, invoice save/recovery, reconciliation, task paging and team tokens; rendering subtrees were measured and mapped, not all manually reviewed line by line.

## Must fix

1. **Scope changes can retain another company's task or team result** (`task_planner.dart:17-53`, `team_access.dart:25-104`).
   - **What this is:** Stateful screens hold fetched rows and invitation results across rebuilds.
   - **Problem:** Reusing the task widget with another company keeps the old future (API replacement is already revalidated by `AccessGate`); reusing the team widget can retain its old future; an in-flight invitation only checks `mounted`. Its returned token can be labelled with the new widget company. The transport's revision check does not detect a widget-company change.
   - **Fix:** Characterize widget replacement and delayed responses. Give each feature an injected repository and view model whose lifetime/scope resets on dependency or company changes. Reject stale completions before publishing.
   - **If we skip it:** Old task rows or an invitation can appear in the wrong workspace UI. Server permissions still protect API operations; this is not evidence of an API authorization bypass.

## Should fix

2. **The API imports a model that imports the API** (`erp_api.dart:9`, `knitting_models.dart:2`).
   - **What this is:** `ErpApi` decodes `KnittingSnapshot`; knitting command models import `ErpException` from the API.
   - **Problem:** Reusing/testing a knitting value or command state pulls in the socket client and all endpoint adapters. The dependency graph has a two-library cycle.
   - **Fix:** Extract shared errors into a UI-free core model library and re-export them through the existing API import for compatibility.
   - **If we skip it:** Data/value tests stay coupled to transport, and future repository boundaries cannot be acyclic.

3. **Two history screens import each other** (`imported_history.dart:8`, `original_production_report.dart:6`).
   - **What this is:** The history register opens the original production report, and the report opens history/detail destinations.
   - **Problem:** Navigation binds both screens into a cycle. A report change can affect history initialization and make isolated reuse harder.
   - **Fix:** Extract shared history values/formatting and inject navigation callbacks or move destination assembly to an app-level adapter. Keep existing routes and labels.
   - **If we skip it:** The history feature cannot enforce a one-way presentation dependency.

4. **Large widgets mix workflow, data and layout** (`knitting_forms.dart:2813`, `document_editor.dart:180`, `invoice_composer.dart:239`, `payment_reconciliation.dart:130`, `pos_checkout.dart:249`).
   - **What this is:** These widgets validate business input, coordinate reviewed writes and reconcile uncertain results while constructing controls.
   - **Problem:** Changing a layout requires navigating financial/stock rules in the same state object. The knitting `_field` method spans 427 lines; measured build methods reach 425 lines. `part` files split text while retaining private-state coupling.
   - **Fix:** Extract one feature at a time. Move state/commands into view models and data/recovery policy into repositories. Keep focus, dialogs and navigation in widgets. Split rendering components by responsibility only.
   - **If we skip it:** Critical behavior is mainly tested through widget setup and is easy to disturb during UI work.

5. **One API class owns unrelated data policies** (`erp_api.dart:68-1601`, `invoice_api.dart`, `imported_history_api.dart`).
   - **What this is:** A 1,601-line client also owns access listeners, session recovery, overview aggregation, document, finance, POS and knitting methods.
   - **Problem:** Every consuming screen depends on the entire concrete client. Test fakes subclass it and construct a real `HttpClient` even when they need one method. Moving invoice/history methods into mixin parts did not introduce data boundaries.
   - **Fix:** Add feature-specific repository contracts using the existing API as the initial service adapter. Migrate callers before splitting authenticated transport/session lifecycle. Do not create one wrapper class per endpoint.
   - **If we skip it:** Small feature changes have a broad dependency surface and repositories cannot be substituted independently.

6. **Request/scope/recovery rules are duplicated** (`invoice_composer.dart:313-452`, `payment_reconciliation.dart:99-118,255-325`, `pending_operations.dart:46-139`, `bank_statement_matching.dart:34-82`).
   - **What this is:** Screens separately compare API/account/company/revision/generation, manage busy state and reconcile prepared/completed/closed operations.
   - **Problem:** The guards already differ: tasks/team omit some lifecycle checks while payment and invoice code have extensive checks. A new access dimension has to be updated in many locations.
   - **Fix:** First pin the distinct outcomes with tests. Centralize a small scope identity and the truly shared recovery policy as features move. Preserve each financial flow's review tokens and acknowledgment timing.
   - **If we skip it:** Stale-result bugs recur and safe write recovery becomes inconsistent. Do not replace these guards with a generic retry helper.

7. **Mutable server maps blur the read/draft boundary** (`native_models.dart:14-27,218-240`, `knitting_models.dart:61-77`).
   - **What this is:** `final` model fields still expose mutable lists/maps; `NativeDocument.editCopy()` is an explicit deep-copy exception.
   - **Problem:** A caller can modify `document.data` or snapshot rows without a repository operation. Other consumers of that object then see changes with no state notification.
   - **Fix:** Introduce immutable read models at repository boundaries, retaining editable copies for forms. Add mutation/copy tests before changing shared dynamic document parsing.
   - **If we skip it:** Rebuilds and draft comparisons can depend on invisible mutation. A whole-app freeze in this audit would risk behavior changes, so none was performed.

8. **Connected rehearsals are outside the default test gate** (`pubspec.yaml`, `tool/pilot_*_test.dart`, absent `.github/workflows`).
   - **What this is:** 84 unit/widget files run by default; 12 static connected/pilot test declarations live under `tool/` and are opt-in.
   - **Problem:** `flutter test` alone cannot establish backend contract, access revocation or real posting/recovery behavior. No repository CI currently enforces architecture or this distinction.
   - **Fix:** Add import/layer checks with negative fixtures and CI for format, analysis, all unit/widget tests and checker tests. Keep a separate verified-native-test rehearsal receipt and fail release acceptance when missing.
   - **If we skip it:** A green default suite can coexist with broken endpoint mapping or an unverified connected workflow.

9. **Architecture roles are hidden by flat names and private parts** (`lib/`, especially `knitting_forms.dart`, `knitting_screen.dart`, `erp_api.dart`).
   - **What this is:** Files are mostly grouped at the root; names such as `native_*`, `mill_*`, `widgets.dart` and `knitting_*` cover several roles.
   - **Problem:** A new task workflow has no clear home, and presentation can import any concrete endpoint. Feature ownership is inferred from prefixes rather than enforced.
   - **Fix:** Feature-first directories and role names (`*ViewModel`, `*Repository`, `*Service`). Preserve established public screen names and use temporary exports so external callers are not broken by a move.
   - **If we skip it:** Architectural rules remain prose that new code can bypass.

## Nice to have

10. **Two shared UI helpers have no callers** (`design.dart:159`, `ui/workspace_ui.dart:103`).
    - **What this is:** `tally` and `WorkspaceSteps` are public utilities.
    - **Problem:** Whole-tree searches found definitions only, with no test, configuration, string-based or runtime construction reference. They add unused UI surface; analyzer does not flag unused public declarations.
    - **Fix:** Remove in the final cleanup after verifying all import/tool consumers again. Do not delete similarly named knitting field constants: they have many same-library callers.
    - **If we skip it:** About 57 lines of unused public surface remain. This is maintenance noise, not a runtime defect.

## Checks and limits

- Baseline `flutter analyze --no-pub`: passed, no issues, 22 seconds on the pinned SDK.
- Baseline full unit/widget suite: running when this audit was written; final receipt belongs in the migration ledger. Static test counts are not pass counts.
- Both cycles were computed from all imports/parts; `part of` backlinks were excluded. Parts are one library, not an independent cycle.
- API review found origin validation, loopback restrictions, timeouts, redirect refusal, safe error text, session invalidation and no automatic write replay. No direct widget-owned socket was found. The unsafe access finding is direct coupling and inconsistent scope lifetime, not evidence that those existing protections are absent.
- No confirmed unused dependency: all direct runtime packages serve a mapped source/platform function. Transitive packages are listed in the inventory. Keep existing state primitives; no evidence justifies a state-management migration.
- Backend financial/stock rules, full source security, performance under production load and OS-native builds are outside this audit. Existing native shell configuration was inventoried through README/build setup; not every generated platform file was manually inspected. No Windows build was run.
- Customer services and live accounts were not used. No assets, copyright headers or upstream source were changed.

Verdict: establish scope-safe feature boundaries first, then separate the high-risk document/finance/knitting command flows under characterization tests. Preserve Flutter state primitives and the existing backend contract.

Lean: approximately 57 lines and zero dependencies can be removed immediately after final reference verification. Further line-count savings are not predicted before behavior-preserving extraction.

Not checked: final suite outcome and connected native-test rehearsals at audit time; production backend load/security and Windows compilation.
