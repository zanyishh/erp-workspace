# General ERP workflow verification

14 November 2026. This audit uses the Flutter application, pinned ERPNext/Frappe source and synthetic data on `native-test.localhost`. It distinguishes an available screen from an operation verified through its resulting documents, stock or accounting entries.

| Workflow | Verified result or boundary |
| --- | --- |
| Purchasing and manufacturing | A submitted purchase requisition mapped to a purchase order for the remaining quantity. A submitted Work Order transferred raw materials to WIP and recorded finished goods in two partial runs. Four units of material produced two finished units. Stores and WIP ended at zero and finished stock at two. Material and output drafts retained their source order. The server rejected over-allocation. Reopening the owner’s completed sales and purchase orders over HTTP confirmed both stopped offering further delivery, receipt, invoicing and advance-payment actions. |
| General subcontracting | A real purchase order for an outsourced service produced the subcontracting order, transfer to the supplier, finished receipt, linked purchase receipt and ₹24 supplier invoice. A linked supplier debit note reversed ₹24. Two finished units appeared in stock. This is the General ERP workflow, available independently of the knitting pack. |
| Serial and batch inventory | With ERPNext’s tracking setting enabled for the test, a material receipt and issue carried the same serial and batch. Their ledger bundles contained +1 and −1 for that unit and the bin ended at zero. Physical scanner and printer trials remain open. |
| Financial reconciliation | The registered owner applied ₹25 of a ₹75 advance to a ₹100 invoice on each side of the ledger, leaving ₹50 unallocated and ₹75 outstanding. Separate statement matching cleared the two bank movements. A mapped CSV import created a ₹65 deposit and a ₹70 withdrawal that were reconciled against the actual payments; repeating the import created zero duplicates. The connected Flutter rehearsals checked both customer and supplier payment paths and the file-import review. |
| Retail | An invited cashier opened a register with ₹100, sold two units for ₹90, and closed at ₹190. The cashier refunded the full receipt during a new shift. ERPNext produced a linked −₹90 credit; replay returned the same credit, and the new drawer closed at ₹10. The two supported invoice modes restored stock from one unit to three. Partial returns, split tender, offline sales, card terminals and receipt printers remain open. |
| Quality and asset maintenance | A purchase receipt with two identical item codes opened an incoming inspection for the selected second row. The first row was unaffected. Completing a due asset calibration through ERPNext scheduled the next monthly log. [Voucher and access checks](2026-11-14-native-accounting-and-maintenance.md) |
| Setup data import | Owners with the underlying import role can download a CSV template and import customers, suppliers and items. Preview checks the headers, links and rows. Confirmation uses original document controllers and rolls back the batch on a bad row. A same-account replay of identical data returns the prior result. A connected Flutter rehearsal previewed, imported and reopened one customer, then retried the same file and found one record. Users can also change the group for up to 50 selected masters; one stale selection aborts the whole change. The importer supports new scalar masters in batches of up to 200 rows / 256 KB. Other bulk edits, child-table import, external sheets and background import jobs remain open. |
| Hierarchies | Permitted tree records expose rename/delete actions with a confirmation and version check. A real Item Group rename kept its child attached. Stale edits, a guest request and deletion of a group with children were rejected. A synthetic leaf could be deleted through ERPNext. Controllers and record permissions govern which trees permit each action. |
| Reports | Sales Order Analysis showed the managed owner’s ₹0 to bill and ₹100 billed. The user opened the source order from its report. Party and status selectors now use their intended values. Tested saved grouped reports cover a single count, sum or average with scoped records. Multi-aggregate or child-table builders and specialised charts still need adapters. |
| Tasks and project templates | A managed owner moved a real task from Open to Working, filtered the board and found it in the calendar. Dependencies prevented a task finishing before its predecessor. A new project copied its template tasks, scheduled their dates and remapped the dependency to the new tasks. |
| Forms | All 1,112 distinct inventoried conditional expressions compile to restricted data, across 2,335 form rule uses and extracted report rules. Tests cover CSV file extensions, child-row flags, company-controlled stock fields and changing parent data. Company and item context now narrow applicable warehouse, account, stock item and Work Order BOM pickers. Coverage of built-in expressions does not establish every DocType's custom buttons or JavaScript workflow. |
| Files and specialised fields | An actual form saved, reopened, displayed and cleared a private file field while preserving the drawn signature and barcode with leading zeros. A Location feature collection supports adding or editing a point while retaining polygons and inherited features. The owner modified bold text on a live Task and reopened its saved HTML; existing formatted descriptions can be displayed and edited without loading embedded network resources. Native map drawing, a fully general rich-text editor and device integration remain open. |
| Finding a task | Catalogue searches such as “receive goods” and “bill customer” reach existing permitted destinations. Search scope and create permission continue to come from the catalogue and selected module. |

## Final checks

All 169 ERPNext backend tests passed on the isolated site. All 214 Flutter tests and eight metadata tests passed. Flutter static analysis reported no issues. The ARM64 Mac release built and passed strict local signature verification. The iPhone simulator debug build and ARM64 Android debug APK compiled. These checks use local services, test devices or simulators, and synthetic data.

## Unverified or outside the local deployment

The earlier inventory lists 835 record types including children and settings, and 198 report definitions. The updated [report inventory](report-extraction.json) finds filter definitions for 172 reports; 136 definitions still flag custom or dynamic behavior. Reports with specific extraction diagnostics fell from 120 to 34. The 34 missing start-date defaults and 27 missing end-date defaults were resolved and fiscal-boundary cases tested. That count identifies candidates and is not a count of currently broken reports. Complete upstream parity also requires verification of document-specific client actions and queries, bulk editing and imports beyond the supported masters, multi-currency and tax/localisation cases, specialised planning and factory configurations, exports/integrations with external providers, assistive technology and physical devices.

Customer-specific textile formulas, vendor print formats and migration equivalence require authorised reference examples. A distribution-ready multi-customer deployment requires per-customer provisioning and public hosting, signing and device testing. Tests here used only the isolated service.
