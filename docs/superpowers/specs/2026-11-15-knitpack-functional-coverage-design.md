# KnitPack functional coverage continuation

The user explicitly directed continuous implementation on 15 November: retain the attractive Flutter interface, restore the breadth and familiar flow of KnitPack, and audit against the existing source research. This continues the approved industry-pack design; no further design approval round is required.

## Approach

Use the existing Flutter/Frappe implementation and source catalogue to make complete workflows discoverable and fill missing operational views. A label-only menu expansion would not supply missing behavior. Replacing the existing backend would discard tested accounting and custody invariants. Reuse existing commands, permission checks, bounded registers and preserved-source readers; add dedicated views and missing contracts where evidence supports them.

The first implementation batch supplies a dedicated estimation register and coherent subcontract area, visible workflow entries for currently buried actions, and a safe commercial-revision path for imported jobs that does not resubmit or alter their original programmes. Later batches address remaining source-linked workflow gaps identified by the same audit, rather than invent source formulas or master facts.

## Required behavior

- Navigation exposes the existing operational tasks with familiar names. Permissions, company selection and setup gates remain authoritative; unavailable operations are never represented as working.
- Estimates have a company-scoped, paged register with number, date, party, status and total where permitted. Open a readable estimate; accept and convert using existing versioned commands. Converted estimates must not silently create a second job.
- Subcontracting presents order, yarn issue, fabric receipt, surplus return, billing and closure as one coherent area, without changing their underlying posting rules.
- Imported commercial revisions preserve original programme IDs, blanks, quantities and dimensions. A rate-only change omits programme payload and still checks expected version, permission and fixed prior-delivery terms. Full programme editing remains unavailable where source semantics cannot be represented safely.
- Historical originals and new operational records are clearly identified; preserved data is not counted twice or presented as a new native transaction.
- Original production has usable grouped reports by original date, saved machine, employee/operator name, shift, customer, fabric and diameter. Totals are exact sums of preserved quantities and recorded counts, with missing values explicitly counted. These reports do not infer valuation, loss, employee identity, consumption or a source vendor formula. Grouping by labels is stated plainly; identical saved labels are grouped together. The report drills back to the same filtered original records.
- Audit every source route against concrete callable behavior and data, not navigation labels. Unproved calculation, provider and destructive behavior stays explicitly unverified.

## Constraints

Only the live source account is available. All source inspection is read-only. No implementation or write test connects to Fashion Suite. All write fixtures use `native-test.localhost`; the customer destination receives no synthetic business data. Preserve all customer originals, native data, audit rows and existing general ERP behavior. Keep services localhost-bound and hosting deferred. Preserve the existing dirty branch and upstream checkouts. No new dependencies are planned.

## Acceptance

Meaningful failing tests precede new command/read contracts and state behavior. Verify company/permission isolation, bounded pagination, stale responses, duplicate conversion, original-programme preservation and navigation. Run relevant real-database suites, the combined Flutter suite and analysis, independent review, then rebuild and inspect the installed app. Update the route ledger and readiness verdict with exact evidence; 100% source equivalence is not established merely by passing synthetic tests.
