# ERP interaction corrections — verification record

16 November 2026. Implementation follows the [researched correction catalogue](../research/2026-11-16-erp-ux-research.md), [source audit](../research/2026-11-16-erp-ux-audit.md), and the user's instruction to implement continuously without another approval round.

## Scope and isolation

- Flutter General ERP and the optional knitting pack share the corrected form, feedback, navigation and recovery behavior.
- Connected work is restricted to synthetic `native-test.localhost` data through Docker context `colima-erp`, Compose project `erp-baseline`. Customer accounts and customer launch profiles are excluded.
- The existing uncommitted application was preserved in place. A 317-file pre-change snapshot is retained in ignored `.local/ux-implementation-2026-11-16/baseline` for scoped comparison; no unrelated changes were staged or committed.
- The app still uses ERPNext/Frappe for permission checks, authoritative calculations and posting. No customer data migration, AI feature, upstream edit or application-volume removal is part of this work.

## Implemented behavior

1. Invoice, generic-document and knitting entry protect edited and in-flight work. Unknown results retain their original reference; supported operations can be checked after leaving or restarting the app.
2. A server journal prepares the operation before a business write, completes with that write, and serializes status/close with mutation. Closing either returns the committed result or prevents the unposted request from running later. It never replays work automatically.
3. Shared forms group permitted schema sections, reveal invalid fields and focus the first correction. Optional disclosure retains controls and values; required, populated and invalid sections remain visible. Expert users can show all sections.
4. Linked-record search debounces input, rejects stale choices/responses and retries without losing the query. Local row removal offers exact Undo, guarded against context and subsequent-sale changes.
5. Lists retain their current query, page and position after opening a record and while refreshing. Applied report filters stay paired with the displayed result and export; new filters do not erase that result before a successful rerun.
6. Submission reviews use only already-permitted server projections. Financial-read restrictions remain in effect. New errors have live semantics and corrective actions.
7. Metrics reflow without shrinking critical numerals. Shared buttons have a 48-logical-pixel minimum. Knitting date/time entry supports picking and typing, strict calendar validation, and signed numeric keyboards.
8. Invoice sample paper keeps a shared identity from gallery to preview. Reduced motion disables that flight. Routine business lists keep ordinary navigation; ornamental staggers and hover lifting are explicitly excluded.
9. Command shortcuts use Command on macOS and Control on Windows; keyboard dialog dismissal restores invoking focus.
10. Invoice review waits for a valid invoice date; delayed company defaults no longer produce an unexplained validation prompt. Users can still choose the date directly.

## Recovery boundaries

The journal covers transactional native documents/workflow actions, invoice draft creation, knitting commands and payment allocation. Site, account and company scope are checked at discovery, replay and result retrieval. Native results are freshly permission-projected; invoice and knitting journal receipts store record/event references. Reconciliation receipts remain server-side and are disclosed only after current permission checks. No financial draft payload is cached locally.

Some administrative or virtual ERPNext controllers commit internally or change schema. Those cannot honestly share the atomic business-write guarantee. A specific schema capability opts those proven types out while preserving their existing save behavior. This is not a guarantee for arbitrary future custom controllers: their transaction behavior must be checked before enabling recovery. Legacy/unsupported operations do not acquire a fabricated durable receipt. POS retains its existing same-token checkout/refund contract.

## Practical limits

Source review and regression tests do not measure a psychological effect or establish a universal usability improvement. The [C01–C60 coverage record](../research/2026-11-16-erp-ux-implementation-coverage.md) distinguishes implemented corrections, retained behavior and applicability limits. Actual native macOS verification is distinct from connected Flutter widget rehearsal. Windows requires a Windows host; mobile-device, VoiceOver/TalkBack, translated-locale/RTL and performance-benchmark results are not claimed without those checks.
